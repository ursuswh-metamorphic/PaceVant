# LOCAL ERC-20 transfer architecture

Checkpoint edd0865c2764115b7fb966d32b5094d63088f4fa. This delivery follows the operator's later instruction to finish the transfer flow and pause dataset selection/evaluation.

The canonical FastAPI app installs operator-only /v1/transfers endpoints. A recipient must first be explicitly configured by the vault owner in configureTransferRecipient. A task is then authenticated through POST /v1/transfers/tasks with exact chain, managed vault, token, recipient, budget, revision, expiry and purpose. Recipient registry permission alone cannot create a payment task.

POST /v1/transfers accepts task ID, revision, idempotency request ID, user goal and an exact amount_base_units. For a one-shot task the exact task budget can supply that amount. Bounded requests must specify it, and any planner expansion is rejected independently of the task ceiling. The configured model proposes a strict TransferProposal. The service checks task identity, unit-safe integer amount, recipient rule, balance, cumulative confirmed spending, one-shot consumption and expiry. Task Shield evaluates the proposal against the operator objective. The existing graph semantic evaluator selects evidence through the existing catalog, with an explicit objective_aliases list to reduce confusion with extracted instructions.

A dedicated transfer SDE requires aligned Shield and graph findings, PASS temporal/risk results, exact local simulation and VERIFIED transfer proof. Swaps retain their existing SDE and ABI. Simulation uses an isolated Anvil fork and an ephemeral simulation attestor. The actual attestor signs only after the transfer SDE approves and the task/state are revalidated. LOCAL transfer valuation uses an explicitly owner-configured reference price with expiry. It does not read live price feeds.

TransferApprovalV2 has a separate transfer-2 EIP-712 domain and binds intent, task terms, policy, evidence, proof, session, token, recipient, amount, nonce, risk and deadline. PolicyVault implements executeApprovedTransferV2 with SafeERC20, exact vault/recipient deltas, unchanged other treasury asset, replay checks and independent recipient/day/task caps. Reverting calls roll back token movement, nonce and successful-spend counters. The transfer path shares USDC daily spending and session/global risk consumption with swaps.

Execution submits the exact signed call. Raw transaction bytes are journaled internally before broadcast. Repeated request IDs return the same durable payment state. Ambiguous submissions remain reserved for read-only reconciliation. Receipt verification checks canonical inclusion, confirmations, sender, vault and the exact contract event, then records actual gas cost and portfolio balances. The task's next request rechecks previous receipt states before consuming historical spend.

The managed source is the configured vault. The runtime requires LOCAL, chain 31337 and an Anvil client. The public Fuji serving mode rejects transfer execution. The emergency withdrawal function remains owner-only and separate. Native AVAX, external EOA custody, transfer web forms and recipient aliases are outside this completed API milestone.

The execution adapter is composed in api/local_transfers.py. Control features consume that injected adapter, and architecture regression tests preserve the existing direct-import boundaries. A shared durable EOA nonce counter is used by swap and transfer submission journals to avoid allocating the same relayer nonce across action types. A crash after nonce allocation can require operator recovery of the retained transaction gap.
